## 1. 显示链路总览

```
相机线程 ──pushFrame──▶ 队列(容量1) ──notify──▶ 工作线程
                                               ├─ barCodeIdentify()
                                               └─ postShowImage() ──排队──▶ 主线程 setPixmap
```

三条原则：

| 原则 | 实现 |
|---|---|
| 生产与消费解耦 | 有界队列 + 条件变量 |
| 显示只关心最新帧 | 队列容量 1，新帧覆盖旧帧 |
| UI 只能主线程改 | 统一 `invokeMethod` 投递 |

## 2. pushFrame：容量 1 的队列

```cpp
void VisionProject::pushFrame(int cam, cv::Mat img)
{
    if (cam < 0 || cam >= 4 || img.empty()) return;

    {
        std::lock_guard<std::mutex> lk(m_mtxDisp);
        std::queue<cv::Mat>& q = m_mapImageData[cam];
        while (!q.empty()) q.pop();     // 丢旧帧
        q.push(img);
    }                                   // 解锁

    m_cvDisp.notify_one();              // 锁外通知
}
```

**关键点**

- **丢旧帧**：显示只需最新画面。不丢则延迟累积、内存增长。
- **`cv::Mat` 拷贝便宜**：引用计数，只拷头部。
- **`lock_guard` 是 RAII**：出作用域自动解锁，异常安全。
- **`notify_one` 放锁外**：避免被唤醒线程立刻抢锁失败。

**面试追问**

| 问 | 答 |
|---|---|
| 为什么容量是 1？ | 旧帧对显示无价值；保证延迟恒定、内存恒定 |
| 丢帧算不算丢数据？ | 显示丢帧是设计选择；算法处理另算 |
| `cv::Mat` 拷贝贵吗？ | 不贵，只拷贝头部和引用计数 |

## 3. displayThdFunc：条件变量等待

```cpp
while (true) {
    int cam = -1;
    cv::Mat img;
    {
        std::unique_lock<std::mutex> lk(p->m_mtxDisp);
        p->m_cvDisp.wait_for(lk, std::chrono::milliseconds(100), [p]() {
            if (p->m_bDispFinish) return true;
            for (int i = 0; i < 4; i++)
                if (!p->m_mapImageData[i].empty()) return true;
            return false;
        });
        if (p->m_bDispFinish) return;
        for (int i = 0; i < 4; i++) {
            if (!p->m_mapImageData[i].empty()) {
                cam = i;
                img = p->m_mapImageData[i].front();
                p->m_mapImageData[i].pop();
                break;
            }
        }
    }                                   // 解锁后做识别和显示
    if (cam < 0) continue;
    ...
}
```

**关键点**

- **`unique_lock` 而非 `lock_guard`**：条件变量要求 `wait` 期间释放/重获锁。
- **谓词防虚假唤醒**：醒来先复查条件，不满足继续睡。
- **100ms 是兜底**：正常靠 `notify` 唤醒，超时只防“通知丢失”导致睡死。
- **锁内只取帧**：识别耗时 30ms，持锁会阻塞生产者。

**面试追问**

| 问 | 答 |
|---|---|
| 为什么不用 `sleep` 轮询？ | 空转烧 CPU、有固定延迟；条件变量“有事才醒” |
| 什么是虚假唤醒？ | 系统可能无故唤醒等待线程，用谓词复查条件防御 |
| 锁粒度为什么这么小？ | 识别耗时，持锁会阻塞 `pushFrame` |

## 4. 识别段：工作线程 + 去重 + 异常

```cpp
static std::string s_lastBarcode[4];    // 每路独立去重

try {
    BarCodeResData ret = p->m_imgProcess.barCodeIdentify(img);
    if (ret.hv_DecodedDataStrings.Length() > 0) {
        QString strCodes;
        for (int k = 0; k < ret.hv_DecodedDataStrings.Length(); k++) {
            HalconCpp::HString hsCode = ret.hv_DecodedDataStrings[k];
            strCodes += QString::fromLocal8Bit(hsCode.Text()) + " ";
        }
        if (s_lastBarcode[cam] != strCodes.toStdString()) {
            s_lastBarcode[cam] = strCodes.toStdString();
            LOG_INFO(QString("相机%1 条码: %2").arg(cam + 1).arg(strCodes));
        }
    }
}
catch (HalconCpp::HException& e) {
    LOG_ERROR(QString("相机%1 条码识别异常: %2")
        .arg(cam + 1).arg(QString::fromLocal8Bit(e.ErrorMessage().Text())));
}
```

**关键点**

- **在工作线程识别**：主线程做会卡界面，采集线程做会拖慢采集。
- **必须 try/catch**：子线程未捕获异常 → `std::terminate` → 进程直接退出。
- **按路去重**：条码持续存在，不去重每秒刷好几行。
- **编码转换**：HALCON 返回本地编码（GBK），用 `fromLocal8Bit`，不能用 `fromUtf8`。

**面试追问**

| 问 | 答 |
|---|---|
| 识别放哪合适？ | 独立工作线程；不能放 UI 线程，也不该放采集线程 |
| 子线程抛异常会怎样？ | 未捕获直接 terminate，程序无提示退出 |
| 为什么要去重？ | 日志可读性；否则每秒多行相同内容 |
| 吞吐瓶颈？ | 单线程串行 4 路，30ms/帧；可拆线程或降采样 |

## 5. postShowImage：UI 只能在主线程改

```cpp
void VisionProject::postShowImage(VisionProject* p, cv::Mat img, int cam)
{
    if (p == nullptr || img.empty() || cam < 0 || cam >= 4) return;

    QMetaObject::invokeMethod(p, [p, img, cam]() {
        QLabel* labels[4] = { p->ui.label, p->ui.label_2, p->ui.label_3, p->ui.label_4 };
        QImage qimg;
        if (img.channels() > 1) {
            cv::cvtColor(img, img, cv::COLOR_BGR2RGB);
            qimg = QImage(img.data, img.cols, img.rows, img.step, QImage::Format_RGB888);
        } else {
            qimg = QImage(img.data, img.cols, img.rows, img.step, QImage::Format_Grayscale8);
        }
        QPixmap pixmap = QPixmap::fromImage(qimg);
        labels[cam]->setPixmap(pixmap.scaled(labels[cam]->size(),
            Qt::KeepAspectRatio, Qt::SmoothTransformation));
    }, Qt::QueuedConnection);
}
```

**关键点**

- **Qt 控件非线程安全**：跨线程改会重绘错乱、崩溃。
- **`QueuedConnection` = 投递到接收者线程的事件队列**，异步执行。
- **`ui.*` 只能在 lambda 内访问**（lambda 在主线程执行）。
- **BGR→RGB**：OpenCV 是 BGR，Qt `Format_RGB888` 要 RGB。
- **`img.step` 不是 `cols*3`**：OpenCV 每行可能有对齐填充。
- **`QImage` 不拷贝像素、`QPixmap::fromImage` 才拷贝**：所以必须在 `img` 存活时 `fromImage`。
- **`p == nullptr` 检查**：退出时主窗口已析构，防野指针。

**面试追问**

| 问 | 答 |
|---|---|
| 为什么 UI 只能主线程改？ | 控件非线程安全，跨线程操作是未定义行为 |
| `invokeMethod` 与信号槽区别？ | 机制相同（事件投递）；前者不需声明信号，可带 lambda，但少了编译期类型检查 |
| `Queued` 与 `Direct` 区别？ | Direct 在调用者线程立刻执行；Queued 在接收者线程排队执行 |
| QImage 为什么危险？ | 只引用源内存不拷贝，源释放后悬垂 |
| 这里的性能问题？ | 每帧 `scaled`（Smooth）开销大；可在尺寸变化时才缩放 |

## 6. 线程退出：通知 + join + 顺序

```cpp
VisionProject::~VisionProject()
{
    // 1) 显示线程
    m_bDispFinish = true;
    m_cvDisp.notify_all();
    if (tDisp && tDisp->joinable()) tDisp->join();

    // 2) 采集线程
    for (int i = 0; i < 4; i++) phk_cam[i]->stopCap();
    if (m_thdSnap && m_thdSnap->joinable()) m_thdSnap->join();

    // 3) socket 线程（recv 阻塞，必须先 closesocket）
    m_socket.stop();
    if (m_thdRecv && m_thdRecv->joinable()) m_thdRecv->join();
    if (m_thdHeart && m_thdHeart->joinable()) m_thdHeart->join();

    // 4) 释放设备（所有使用者已停）
    DeviceManager::getInstance().relaseDev();
    delete m_doc;
}
```

**关键点**

- **不能 `detach`**：线程函数持有 `this`，对象销毁后访问即野指针。
- **`join` 会阻塞到线程函数 return**。
- **`joinable()` 判断**：未启动或已 join 的线程不能再次 join。
- **`m_bDispFinish` 用原子**：跨线程读写，普通 `bool` 是数据竞争。
- **阻塞在 `recv` 的线程**：只置标志无效，必须 `closesocket` 打断。
- **睡眠拆小步**：心跳 10s → 50×200ms，退出不必等满 10s。
- **顺序不能颠倒**：先停使用者，最后释放资源。

**面试追问**

| 问 | 答 |
|---|---|
| 为什么 join 不 detach？ | 保证对象销毁前线程已结束 |
| 只置标志为什么无效？ | `wait` 的线程不知道内存变了要 notify；`recv` 阻塞在内核要 closesocket |
| `atomic` 与 `mutex` 怎么选？ | 单标志用 atomic（无锁）；多字段一致性用 mutex |
| 线程卡死怎么办？ | 实际项目加超时/强制终止；本项目靠可中断睡眠保证及时退出 |

## 7. Logger：日志模块

```cpp
void Logger::log(Level lv, const QString& msg)
{
    const QString ts = QDateTime::currentDateTime().toString("HH:mm:ss.zzz");
    const QString line = QString("[%1][%2] %3").arg(ts).arg(lvText).arg(msg);

    {
        QMutexLocker locker(&m_mtx);        // 锁保护文件
        // 跨天换文件
        m_file.write(line.toUtf8());
        m_file.write("\n");
        m_file.flush();                     // 立刻落盘
    }                                       // 锁外发信号

    emit newLog(line);                      // 接收者在主线程 → 排队的信号
}
```

**关键点**

- **单例**：全局一份文件 + 一把锁；C++11 局部静态初始化线程安全。
- **锁保护文件**：多线程并发写会内容交错。
- **每行 `flush`**：崩溃后日志仍在（可靠性优先于性能）。
- **按天分文件**：`logs/yyyy-MM-dd.log`，追加模式。
- **写 UTF-8**：日志给别人看，避免 GBK 乱码。
- **锁外 emit**：槽函数里若再写日志会自锁死。
- **`QueuedConnection`**：`log()` 可能在工作线程，界面更新必须回主线程。

**面试追问**

| 问 | 答 |
|---|---|
| 单例线程安全吗？ | C++11 起局部静态初始化由编译器保证只执行一次 |
| 为什么每行 flush？ | 崩溃后能查到日志；牺牲性能换可靠性 |
| 为什么锁外发信号？ | 避免槽函数内递归写日志导致死锁 |
| 已知不足？ | 无大小切分、无级别过滤、同步写文件、无异步落盘 |

## 8. DeviceManager：继承 / 工厂 / 单例

```cpp
Camera* DeviceManager::creatCamIns(int camType)   // 工厂
{
    if (camType == HK_CAM)      return new HK_Camera();
    if (camType == BALSER_CAM)  return new Balser_Cam();
    LOG_ERROR(...); return nullptr;
}

Device* DeviceManager::getDevice(int type)        // 查询用 find
{
    std::lock_guard<std::mutex> lk(m_mtx);
    auto it = m_mapDev.find(type);
    return it == m_mapDev.end() ? nullptr : it->second;
}

void DeviceManager::addDevice(Device* dev, int type)   // 登记用 insert
{
    std::lock_guard<std::mutex> lk(m_mtx);
    auto ret = m_mapDev.insert(std::pair<int, Device*>(type, dev));
    if (!ret.second) LOG_WARN(...);   // 已存在，不覆盖
}
```

**关键点**

- **虚析构**：通过 `Device*` 删派生类对象，必须 `virtual ~Device()`。
- **工厂**：调用方只认识 `Camera*`，不依赖具体类。
- **单例**：私有构造 + 删除拷贝/移动 + 局部静态。
- **`find` 而非 `operator[]`**：后者在键不存在时会插入 `nullptr`，污染设备表。
- **`insert` 而非 `operator[] =`**：后者会覆盖，旧指针泄漏。
- **加锁**：设备表可能被多线程访问。

**面试追问**

| 问 | 答 |
|---|---|
| 基类为什么要虚析构？ | 否则基类指针 delete 派生类对象时派生类析构不执行，资源泄漏 |
| 单例的缺点？ | 全局状态、隐藏依赖、难测试 |
| `operator[]` 和 `find` 区别？ | `operator[]` 不存在会插入默认值；`find` 只读 |
| 为什么返回裸指针？ | 现有接口风格；更现代是 `unique_ptr` |
| `map` vs `unordered_map`？ | 需有序用 `map`；纯查找用 `unordered_map`（平均 O(1)） |
